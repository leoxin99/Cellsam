## 2. 层级结构与决策权

```
Level 0  用户                        → 最终决策权，Go/No-Go
Level 1  审核 Agent (R1)             → 质量门禁，SSOT 回填权
Level 2  实施 Agent (A1, A2)         → 代码与实验执行权
```

**决策升级规则**:
- 实施 Agent 完成任务 → 产物交用户 → 用户转交审核 Agent
- 审核 Agent 通过 → 回填文档 → 闭环
- 审核 Agent 不通过 → 问题清单交用户 → 用户转交实施 Agent 修复
- 重大方向变更 (如放弃 Phase 2) → 必须由用户决定

### 2.1 审核意见响应原则

> ⚠️ **核心规则**: R1 审核结论是**建议**，不是命令。A1/A2 作为执行者最了解任务上下文，**必须独立判断**每条建议。

**A1/A2 收到 R1 审核意见后的响应流程**:

1. **逐条评估**，对每条建议明确标注:
   - ✅ **采纳** — 简述原因
   - ❌ **拒绝** — 给出具体反驳理由（R1 可能缺乏哪些上下文？建议为什么不适用？）
   - ⚠️ **部分采纳** — 说明采纳哪部分、修改了什么

2. **反驳时的要求**:
   - 必须给出**具体技术理由**，不能只说"不同意"
   - 引用代码/数据/实验结果作为支撑
   - 如果 R1 审核基于过时信息，指出哪里过时

3. **将评估结果写入 inbox 回复**，格式示例:
   ```
   ## A2 → R1 — 对 Fix3 审核意见的评估
   - R1 建议 1 (保留 ep3 checkpoint): ✅ 采纳，Dice +2.7% 值得保留
   - R1 建议 2 (取消 A100 Job): ❌ 拒绝，A100 对比数据对论文消融表有价值
   - R1 建议 3 (转向 baseline): ⚠️ 部分采纳，先完成 phase2_design 回填再转向
   ```

**R1 的责任**:
- 审核意见应注明置信度，区分"确定性问题"(如数值错误) 和"建议性意见"(如方向判断)。
- **优先级判断的依赖性检查**: 当因某任务终止而建议降级其他任务时，必须先回答:
  > **被降级的任务是否真正依赖被终止的任务？** 如果二者属于不同子系统 (如 检测 vs 分割、训练 vs 推理)，不能因一个终止而降级另一个。
  >
  > 反例 (已发生): "P2-A 训练终止 → Adaptive 检测优化暂缓" — 错误，因为检测框优化对所有训练方案都有正面影响。

### 2.2 审核意见回复模板 (A1/A2 固定格式)

> 用法: A1/A2 收到 R1 审核意见后，复制以下模板到 `docs/agent_inbox.md`，逐条填写，不允许空项。

```markdown
## [YYYY-MM-DD HH:mm] A1(Codex)/A2(Claude) -> R1(Reviewer) — 对 <review_task> 审核意见的逐条评估

- **source_review**: <review_path_or_inbox_ref>
- **scope**: <本次评估覆盖范围>

1) R1 建议: <建议1原文摘要>
- 结论: ✅ 采纳 / ❌ 拒绝 / ⚠️ 部分采纳
- 理由: <技术理由，必须具体>
- 证据: <代码路径:行号 / 实验结果文件 / 指标数值>
- 动作: <将执行或已执行的动作>

2) R1 建议: <建议2原文摘要>
- 结论: ✅ 采纳 / ❌ 拒绝 / ⚠️ 部分采纳
- 理由: <技术理由>
- 证据: <同上>
- 动作: <同上>

3) R1 建议: <建议3原文摘要>
- 结论: ✅ 采纳 / ❌ 拒绝 / ⚠️ 部分采纳
- 理由: <技术理由>
- 证据: <同上>
- 动作: <同上>

- **summary**:
  - 采纳: <n>
  - 拒绝: <n>
  - 部分采纳: <n>
- **status**: ✅ 已闭环 / ⏳ 待执行 / 🚫 阻塞
```

**强制校验**:
1. 出现 `❌ 拒绝` 时，必须附带可验证证据（代码或实验数据），否则视为无效回复。  
2. `⚠️ 部分采纳` 必须写明“采纳哪部分 + 不采纳哪部分”。  
3. 回复发出后，若涉及代码/文档改动，需同步回填对应 SSOT 文档。

## 3. 沟通机制

### 3.1 通信拓扑

Agent 之间**无法直接通信**（各自独立的 Antigravity 窗口）。通过三个信道协作:

| 信道 | 实时性 | 内容 |
|------|--------|------|
| **用户口头中转** | 实时 | 紧急指令、Go/No-Go 决策 |
| **Agent 信箱 `docs/agent_inbox.md`** | 异步 | 产物摘要、审核结论、任务交接 |
| **共享文件系统 (Git Repo)** | 异步 | 代码、实验结果 JSON、文档 |

> ⚠️ **Inbox 规则 #5** (2026-02-25 新增): R1 审核结果**必须先写入 inbox**，再通知用户。详见 `agent_inbox.md` 归档规则。

### 3.2 产物提交格式 (实施 Agent → 用户 → 审核 Agent)

实施 Agent 完成任务后，向用户提交的摘要**必须包含**:

| 字段 | 说明 | 示例 |
|------|------|------|
| `commit_sha` | 最近一次相关 commit | `a3f2c1d` |
| `cmd` | 执行的命令 | `python tools/ablation_detection_e34b.py` |
| `config_path` | 使用的配置文件 | `src/config/phase2a_neighbor_overlap.yaml` |
| `split` | 数据划分 | `val(71)` / `test(73)` |
| `output_path` | 产物文件路径 | `experiments/ablation_detection_e34b/results.json` |
| `key_metrics` | 关键数值 | `F1=0.8106, P=0.7639, R=0.8633` |
| `regression` | 回归测试结果 | `10 passed, 0 failed` |
| `modified_files` | 修改的文件列表 | `src/detection/dapi.py:71,231,539` |

### 3.3 审核报告格式 (审核 Agent 输出)

文件路径: `docs/temp_reviews/<experiment>_review.md`

必含章节:
1. **审核结论** — 通过 / 有条件通过 / 不通过
2. **代码验证** — 参数链路、逻辑正确性
3. **实验验证** — 数值核对、搜索空间覆盖、策略合规
4. **关键发现** — 如参数退化、泛化性分析
5. **下一步建议** — 回填清单或修复清单

### 3.4 SSOT 文档阅读规则

> ⚠️ **强制规则**: 所有 Agent 读取 SSOT 文档时，**必须先看 outline 或完整阅读**。
> **禁止**仅读取前 N 行就下结论。原因: 重要章节可能在文件后半部分（如 `task_backlog.md` 的 §3.5 在 L104+）。

操作方式:
1. 首次读文件 → 使用 `view_file_outline` 获取全文结构
2. 或直接 `view_file` 不限行数（≤800 行的文件一次读完）
3. 检查工具返回的 `Total Lines`，确认已读完全文

### 3.5 主动要求信息规则

> ⚠️ **强制规则**: 当用户提出的任务或问题**缺乏足够信息**来准确、高质量地执行时，Agent **必须主动向用户索要更多信息**，而非擅自假设或猜测。

适用场景:
1. **任务范围不明确** — 用户说"优化一下"但未指定优化方向或约束
2. **技术细节缺失** — 缺少必要的参数、配置、数据集信息
3. **多种可行方案** — 存在多种同等合理的实现路径，需用户决策
4. **依赖外部信息** — 需要论文内容、导师意见、数据位置等 Agent 无法自行获取的信息

操作方式:
- 在 `agent_inbox.md` 中或直接通过对话向用户提出具体问题
- 问题须明确、具体，列明已知信息和需要补充的信息
- **不允许**在信息严重不足时默默执行并产出低质量结果

### 4.2 并发冲突防护 (A 模式约束)

审核 Agent 执行文档回填**前**，必须确认:

1. 实施 Agent 无未 commit 的文档修改（用户口头确认或 `git status` 干净）
2. 回填范围声明：审核 Agent 在开始回填前列出将要修改的文件清单
3. 回填完成后通知用户，用户可转告实施 Agent "文档已更新，请 `git pull`"

### 4.3 `docs/temp_reviews/` 清理规则

- 审核通过 + 结论已合并进 SSOT 文档 → **可删除**对应报告
- 审核不通过 → 保留至修复闭环后再删
- 建议月度清理

## 5b. 代码文档规范 (Code Documentation Standard)

> ⚠️ **强制规则** (2026-03-01 起生效): 所有新增的 Python 脚本/模块**必须**在文件开头包含来源说明。

**格式要求**: 文件开头的 docstring 必须包含以下字段:

```python
"""
<脚本名称/用途 — 一句话摘要>

背景 (<日期>, <创建者 Agent ID>):
  <为什么创建这个文件? 对应哪个 Task/问题?>

目的:
  <这个脚本做什么? 列出 1-3 个要点>

依赖:
  <需要哪些数据/文件/环境?>

结果记录在: <对应文档路径>
"""
```

**适用范围**:
- `src/` 下所有新增模块
- `tools/` 下所有新增脚本
- `scripts/` 下所有新增 SLURM/Shell 脚本 (用 `#` 注释)
- 不适用于修改已有文件 (但鼓励补充)

**示例**: 参见 [`tools/_compare_weights.py`](../tools/_compare_weights.py)
